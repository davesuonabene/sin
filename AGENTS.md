# Project guidance

## GAIA library ownership and storage

GAIA is the sole library-management application. The SIN node editor is a read-only consumer of GAIA assets: it may select a vault and browse, preview, or use its assets in nodes, but must not create, edit, import, scan, tag, organize, delete, or otherwise manage vaults or library assets. Implement all library-management UX and workflows in GAIA.

Each item has exactly one owning vault. A vault is a 1-1 physical reflection of its local storage directory (`<vault_store>`, e.g., `assets/vaults/<storage_key>/` or `<custom_root>/<storage_key>/`) combined with tracked external references. Opening `<vault_store>` in the OS file explorer matches the folder hierarchy shown in GAIA Manager, except without uncollected `external_reference` items, which remain at their original external paths (displayed in italic) until the user chooses **Collect into vault** (`POST /items/collect`). External folders are tracked via **Vault Mirrors** (`vault_mirrors` table) in either `reference_1to1` mode (1-1 read-only external references) or `distill_copy` mode (flattening and copying new/updated files into `<vault_store>` with non-destructive `.NN` versioning and subfolder conflict disambiguation). Never rename, move, overwrite, tag in place, delete, or create derivatives beside an external reference without explicit user confirmation. Every materialized copy, project, and derivative must be created inside the owning vault; deleting an external reference deletes only GAIA's database record. A vault's `storage_key` is the unique normalized name established at creation; do not add numbered keys, virtual memberships, or path fallbacks. Profiles belong in `.gaia/profiles/`, outside the asset store.

Projects are typed folders (`type = "project"`) directly inside their owning vault. They own relationship context and generated files under `files/<stage>/`; sources remain imported assets without GAIA-created files. Adopting an external reference into a project copies it into the project first, verifies and publishes the managed copy, and only then updates GAIA ownership; adoption never removes or alters the external source. Use generic `ItemReference` edges for every relationship, stage, revision, use, and master—do not create asset-specific relationship tables. The domain has no `live_recording` type: generic `audio` is the base; `track` and `sample` are children (`sample.is_loop` is sample metadata), and `zoom_h4` (`ZoomH4Item`) is a child of `multitrack` (`MultitrackItem`).

Normal folders in a vault (`FolderItem`, `type = "folder"`) correspond 1-1 to physical directories on disk (or external directories for uncollected `1-1 Reference` mirrors), while folders inside a `ProjectItem` remain logical organizational bins. Normal deletion (`Delete` / `Backspace`) of a vault `FolderItem` deletes the folder and its contents (physically deleting `managed` files/directories inside `<vault_store>`, untracking `external_reference` DB rows without touching external files on disk, and safely preserving/moving any descendant item referenced by an external `ProjectItem`). A separate explicit **Dissolve folder** action (`POST /items/folders/{folder_id}/dissolve`) moves direct children into the parent folder (`folder.parent_id`) and removes only the dissolved folder container. Playlists are ordered horizontal views across vaults (`playlists` / `playlist_items`).

## Node architecture and polymorphism

All node-specific rendering, styling, badge identifiers, default property initialization, and property inspector tab configurations must be encapsulated directly within `BaseNode` subclasses in `editor/src/nodes/`.

- When creating or modifying a node type, extend `BaseNode` and declare static class metadata (`defaultColor`, `defaultIcon`, `badgeLabel`, `nodeType`, `defaultTab`, `tabs`, and `fields`). `BaseNode` resolves dynamic fallbacks through its getters.
- Do not add external `if (node.type === ...)` switches in `editor/src/main.ts` or `editor/src/ui/PropertiesWindow.ts`. Delegate to node instance methods and getters such as `node.drawCanvas(ctx, canvas)`, `node.badgeLabel`, `node.propertiesTabs`, and `node.defaultPropertiesTab`.
- All frontend canvas node implementations inherit from `BaseNode` for consistent hit testing, action overlays, and drawing contracts.

## Parameter fields and inspector widgets

Declare node parameters as `FieldSchema[]` on their node class. Inspector panels render controls through `WidgetFactory.createRow(field, node, onChange)` and declare layouts through `static panelSchema: NodePanelSchema`. Change node state only via `node.updateProperty(key, value)` or `node.properties` so the UI and serialized payload remain aligned.

## Multi-slot node addressing, deterministic seeds, and preview synchronization

- **Dynamic Node Slots (`node[n]`)**: `SampleNode` and `SequenceNode` maintain dynamic slot arrays (`properties.slots: NodeSlot[]`) created and removed in the Inspector (`+` positioned directly next to the active slot pill) and selectable as `[0] [1] ...` pills in both the Inspector and IRIDE canvas overlays. Downstream connected nodes address upstream slots deterministically with modulo wrapping (`idx % S`): `SequenceNode` via its global `sample_slot` pattern field (supporting integer literals, whitespace-separated looping sequences like `"0 1"`, and `"rand"`), and `ArrangementNode` via per-section `section_slots`.
- **Non-Cascading Deterministic Seeds**: Procedural variation is driven by explicit `seed` fields (`type: 'seed'`) paired with a right-hand Refresh Toggle (`seed_refresh`, default `true`) using the shared `mulberry32` + FNV-1a PRNG in `ermes/ts/slotLanguage.ts` and `ermes/py/slot_language.py`. Pressing Refresh (`↻`) runs `refreshArmedSeeds`, rolling only armed seeds (`seed_refresh !== false`) when Global Freeze is off and immediately populating all `slots[0..S-1]` from attached Asset Pools and Random modifiers. Pressing Play (`Space` / Global Play) or Node Preview (`▶`) never advances seeds or mutates the visual preview.
- **Lockstep Audio/Visual Preview Pipeline**: Progressive bar chunks are staged off-screen via `GaplessAudioScheduler.stageBarChunk(chunk, sessionId)` without starting playback on bar 0 or overwriting `fullAudioBuffer` with partial buffers. When streaming completes, `commitSession(sessionId)` publishes the full buffer, `distributeWorkspaceManifest` awaits all intermediate stem buffers, and `playFromStart()` / `playAsync()` awaits `AudioContext.resume()` before starting transport and visual telemetry together.
